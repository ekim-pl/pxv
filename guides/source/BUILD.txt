pxv guide build

Authoritative sources: operator-en/pl.md, user-en/pl.md, quickstart-en/pl.md and
credentials-en/pl.md under source/markdown. The edition list is configured once
in build-manifest.json. Quickstart is the phone-sized guide supplied with every device;
credentials is a blank private insert template, never a populated public export.
Theme: assets/brand.json with the same brandName as product.json.

From the matching source checkout, with pinned dependencies installed:
  pxv guides rebuild --chromium /usr/bin/google-chrome
For HTML only:
  pxv guides rebuild --html-only
For another destination:
  pxv guides rebuild --output-dir output/pdf --chromium /usr/bin/google-chrome
For an installation-specific phone-sized booklet and blank credential insert:
  pxv guides rebuild --policy policy-packs/fleet-nerd/policy.json --output-dir output/pdf/fleet-nerd --chromium /usr/bin/google-chrome

--policy validates a authoring policy. Choose
a separate --output-dir; policy builds cannot overwrite authoritative sources.
Relative paths resolve from the caller's directory. No project is required.
Use the real installation policy in place of the fleet-nerd starter example.

Policy builds adapt single-Owner instructions, add one quickstart appendix section
per configured GrapheneOS profile and include paired ordinary credential and
account/recovery sheets per profile. For N profiles, quickstart has 8 + N sections
and the insert has 2N + 2 sections. A single Owner produces 9/4 sections; five profiles
produce 13/12 sections. Names, roles, language and declared configuration are
intended settings, not device verification. Secrets remain blank; the input
policy and private registry are not copied into public guide outputs. Generated
Markdown in the destination records the rendered source without personalizing
the shared source files. Without --policy, the generic quickstart has eight sections
and the credential insert has four sections.

The command builds the workspace, then calls tools/optional/publishing/rebuild.mjs.
Installed packages contain guide sources and build configuration, not the renderer.
No browser download, dependency installation, device access or publication occurs.

Operator/user editions create HTML, an A4 office PDF and a 216 x 303 mm print
PDF with A4 trim and 3 mm bleed. Quickstart/credentials create HTML and one
-a4-fold.pdf with landscape A4 sheets (297 x 210 mm). Each sheet contains four
136 x 100 mm slips, each folding to 68 x 100 mm. Panels are rendered at actual
size before imposition; content reflows without reducing the 10 pt body font.
Metadata is at least 8 pt; writing fields reserve 8 mm below each label.
Sections may span several panels. The QA manifest records physical sheets,
logical panels, group separation and placement coordinates. Stale A5 office/
print PDFs are removed by PDF rebuilds. Operator/user bleed PDFs are not PDF/X.

Print folded packets single-sided, landscape A4, actual size / 100%. Disable
fit-to-page and booklet mode. Measure the 50 mm scale. Cut solid lines and fold
dashed lines with printing inside. Stack by slip and panel number. Blank panel
positions remain empty. Keep quickstart, ordinary credentials and erasure records
on separate sheets; detach and seal destructive slips separately. Generic inserts
need ordinary profile sections copied for each actual profile; policy builds
create those sections automatically. Check actual sheet counts in qa/manifest.json.
Mark optional erasure not configured unless actually configured and agreed.
Complete inserts privately by hand, seal for the recipient and match asset labels.
See guides/README.md for the full pack-every-device procedure.

PDF builds require an explicitly selected Chromium and Poppler tools pdfinfo,
pdftotext, pdffonts and pdftoppm. Rendered-source/output hashes, extracted text, page counts, font checks,
page boxes and one PNG per page are recorded in qa/manifest.json. --no-render
skips PNG generation; --html-only does not run Chromium or Poppler.

Review every rendered page before distribution. QA records describe only the
actual document build. Device status belongs to the project handoff report.
Keep policy-build source provenance with the reviewed output and accepted report.
Generated guide files and qa/ are local build outputs; keep reviewed copies with
the matching release. Never put credentials or device-specific records in guides.
